## 1. שירות הנתונים: הורדה יומית של כל המחירונים

אפיון מפורט, עלויות והחלטות: [DATA-PIPELINE.md](DATA-PIPELINE.md).

### 1.1 מקורות
חוק שקיפות המחירים מחייב כל רשת לפרסם מחירון מלא (PriceFull), מבצעים (PromoFull), רשימת סניפים (Stores) ועדכונים תוך-יומיים (Price/Promo delta). המקורות שכבר ממומשים ב-`scripts/fetch-prices.mjs` (✅): שופרסל (Azure blobs), publishedprices.co.il (רמי לוי, יוחננוף, טיב טעם, קשת, ועוד עשרות רשתות עם שם משתמש ציבורי), קרפור (prices.carrefour.co.il), חצי חינם. חסר (🔲): laibcatalog (ויקטורי, מחסני השוק - מחזיר ריק כרגע), אושר עד, יינות ביתן/מגה, דור אלון, סופר-פארם, זול ובגדול, פרשמרקט, סטופ מרקט, ועוד ~15 רשתות קטנות. מקור מרוכז: הרשימה הרשמית של משרד הכלכלה (~30 רשתות).

### 1.2 היקף
- ~30 רשתות, ~2,500-3,000 סניפים. PriceFull לסניף: 8,000-30,000 שורות. סה"כ **~40 מיליון שורות מחיר ביום**, ~2-4GB קבצים דחוסים ביום.
- לא צריך לשמור הכל כטבלה: שומרים **מצב נוכחי** לכל (סניף, ברקוד) ו**היסטוריית שינויים** בלבד (רוב המחירים לא משתנים יום-יום). מצב נוכחי: ~40M שורות, ~3-5GB ב-Postgres עם אינדקס (ברקוד, סניף). היסטוריה: קטנה יחסית.
- קבצים גולמיים לארכיון ב-object storage זול (R2/S3) לפי תאריך, לצורך שחזור ו-audit.

### 1.3 ארכיטקטורה
1. **Runner** במכונה שאינה ענן ציבורי (הפורטלים חוסמים IP של ענן; ✅ נלמד): מיני-PC/מחשב בבית או VPS ישראלי. cron ב-03:00. Playwright למקורות שדורשים דפדפן.
2. **Fetch**: לכל רשת → רשימת קבצים של היום → הורדה מקבילית עם retry → S3. רשימת סניפים (Stores) פעם בשבוע. סטטוס לכל רשת (הצליח/נכשל/כמה קבצים) לטבלת `pipeline_runs`.
3. **Parse** (✅ `src/catalog/priceXml.js`, לתמוך גם ב-UTF-16 ובפורמטים השונים): XML → שורות {chain, store, gtin, name, manufacturer, unit, qty, price, unitPrice, isWeighted, updatedAt}. מבצעים → חוקי תמחור (2 ב-, השני ב-50%, מועדון).
4. **Load**: upsert למצב הנוכחי, כתיבת delta להיסטוריה. מוצר חדש (ברקוד לא מוכר) → תור להעשרה (שם מנוקה, קטגוריה, מושג, תמונה).
5. **Build**: ✅ `products.json` + קטלוגים רזים לאונליין; 🔲 אינדקס לשירות בסניף (ברקוד → מחיר בכל סניף) נשאר ב-DB ולא בקובץ.
6. **Serve**: API עם Postgres (Neon/Supabase) במקום קבצים סטטיים; Vercel נשאר ל-frontend ול-API הדק.
7. **ניטור**: לכל רשת - מתי עודכנה לאחרונה, כמה סניפים, כמה מוצרים, סטיות (ירידה של 30% במספר המוצרים = תקלה). דשבורד באתר הניהול + התראה.

### 1.4 מודל נתונים (ליבה)
```
chains(id, name, kind[online|store|both], portal, ...)
stores(id, chain_id, external_id, name, address, city, lat, lng, type[store|online], is_active, updated_at)

```

### 1.5 גיאוקידינג סניפים
קובץ Stores כולל כתובת ועיר. גיאוקוד חד-פעמי (Google Geocoding / Nominatim) → lat/lng. ~3,000 סניפים = זניח בעלות. סניפים ללא כתובת תקינה → תור לתיקון ידני באתר הניהול.

## 2. קטלוג, מושגים ותחליפים

### 2.1 קטלוג מוצרים
- מפתח = ברקוד (GTIN). ✅ 4,000 מוצרים שנמכרים ב-3 רשתות לפחות. 🔲 להרחיב ל-כל המוצרים שמופיעים ב-2 רשתות לפחות (עשרות אלפים) עם דפדוף וחיפוש ב-DB במקום קובץ.
- העשרה: שם נקי (השמות בקבצים קצוצים ✅ ידוע), מותג, קטגוריה (605 "כללי" היום), תמונה (מ-API של אתרי הרשתות שכבר נסרקים), מותג פרטי (שופרסל, רמי לוי, קרפור מסמנים במחירונים; אפשר גם לפי יצרן).
- העשרה בעזרת LLM במנות (offline): מהשם הקצוץ + היצרן → שם מלא, קטגוריה, מושג, גודל. בדיקת עקביות מול 3 רשתות.

### 2.2 שכבת מושגים ("חלב", "קמח")
- מושג = מה שהלקוח מתכוון כשהוא כותב מילה אחת: `חלב` → "חלב 3% 1 ליטר בקרטון", עם חלופות (1%, שקית, 2 ליטר).
- רשימה כללית (טקסט חופשי/קול/קבלה) מתורגמת ל**מושגים + כמויות**, לא לברקודים. הברקוד נבחר לכל סניף בנפרד: המוצר הזול שעונה למושג, או המותג המועדף של הלקוח אם יש לו כזה בהיסטוריה.
- זה מה שמאפשר "הסל הכללי שלך עולה ₪412 ברמי לוי ו-₪467 בשופרסל" גם כשהמוצרים הספציפיים שונים.
- בניית המושגים: ~500 מושגים מכסים 90% מהסלים. חצי-אוטומטי (LLM מציע, אדם מאשר באתר הניהול).

### 2.3 תחליפים
מתי מציעים: (א) המוצר לא קיים/אזל בסניף או באתר; (ב) יש מותג פרטי זול יותר באותו מושג; (ג) הלקוח כתב מושג כללי.
איך בוחרים: אותו מושג, אותו גודל ±25%, אותה כשרות אם המשתמש סימן, תמיד מוצג הפרש המחיר ("₪3.90 במקום ₪6, חיסכון ₪2.10"). מותג פרטי מסומן. העדפת המשתמש נשמרת ("תמיד להחליף במותג פרטי" / "אף פעם" / לשאול). באתר הרשת: ✅ הפריט שלא נמצא מדווח, 🔲 התחליף מועבר במקומו אחרי אישור.
תצוגה: בסל, שורה קטנה מתחת לפריט: "יש זול יותר: X ₪Y [החלף]". במסך ההשוואה: "3 תחליפים חסכו ₪12".

## 3. שירות הקנייה בסניף

1. הלקוח בונה רשימה (מושגים או מוצרים). נותן מיקום (GPS או עיר) ורדיוס (ברירת מחדל 5 ק"מ, ניתן לשינוי).
2. המנוע מתמחר את הרשימה מול כל סניף ברדיוס (בדרך כלל 10-40 סניפים): סכום, כמה פריטים חסרים, מבצעים, מחיר מועדון (מסומן בנפרד).
3. תוצאה: רשימת סניפים ממוינת לפי מחיר עם מרחק, "חסר X פריטים", ומפה. "החיסכון לעומת הסניף הקרוב ביותר: ₪Y".
4. **רשימת קנייה בסניף** (PWA, מובייל): פריטים לפי קטגוריה (סדר מחלקות טיפוסי), סימון V, המחיר הצפוי ליד כל פריט, סה"כ רץ. ✅ אפשרי בלי שום הזרקה, לכן זה השירות הראשון שעובד טוב בנייד.
5. בסניף: סריקת ברקוד → "המחיר כאן ₪X, במחירון ₪Y" (בדיקה שהמחירון נכון + דיווח פערים). 💡 פיצול בין 2 סניפים כשזה משתלם.
6. אחרי הקנייה: העלאת קבלה → אימות מול המחירון, עדכון "המותג המועדף" מהקנייה בפועל, היסטוריה.

## 4. דרכי קלט לרשימה
- ✅ חיפוש מוצר + קטגוריות.
- 🔲 **טקסט חופשי**: "חלב, 2 קמח, ביצים L, במבה 3" → LLM → מושגים+כמויות → הצגה לאישור עם אפשרות לבחור מותג. תמיכה בשגיאות כתיב ובעברית מדוברת.
- 🔲 **קול**: הקלטה בדפדפן (Web Speech API בעברית ב-Chrome; ב-Safari/מובייל - הקלטה ושליחה ל-STT בשרת) → אותו מסלול כמו טקסט.
- 🔲 **קבלה** (צילום/PDF): מודל ראייה → שורות (שם, כמות, מחיר, לפעמים ברקוד) → התאמה לקטלוג (ברקוד אם יש, אחרת שם+מחיר+רשת) → רשימה. שימוש נוסף: "הסל האחרון שלך מהקבלה עלה ₪X, היום הוא ₪Y ב-Z".
- 🔲 **היסטוריית הזמנות מהרשת**: הסימנייה בדף ההזמנות של הרשת קוראת את הפריטים (אונליין בלבד).
- 🔲 **סריקת ברקוד** במצלמה (מובייל) להוספה מהמזווה.
- 💡 שיתוף רשימה בין בני בית (קישור), רשימות קבועות ("שבועי", "שבת", "מסיבה").

## 5. מנוי, קופונים ואתר ניהול

### 5.1 חשבונות
- הרשמה בטלפון (OTP ב-SMS, מקובל בישראל) או Google. מייל אופציונלי להתראות.
- פרופיל: עיר/כתובת ברירת מחדל, רדיוס, כשרות, העדפת תחליפים, מותגים מועדפים (נלמדים).
- הסל והרשימות עוברים מ-localStorage לחשבון (סנכרון בין מכשירים).

### 5.2 מנוי ₪10 לחודש
- חינם: בניית רשימה והשוואה בסיסית (למשל 2 רשתות / סניפים) - חייבים "טעימה" כדי להמיר.
- מנוי: כל הרשתות והסניפים, העברה לאתר הרשת, התראות, היסטוריה, קבלות.
- סליקה: ספק ישראלי (PayPlus / Cardcom / Grow) או Stripe. הוראת קבע חודשית, ביטול בלחיצה, חשבונית מס אוטומטית.
- **תקופה חינמית גלובלית**: באתר הניהול "פתוח לכולם עד תאריך X" - כל נרשם מקבל מנוי מלא בלי כרטיס. שימוש: השקה, קמפיין.
- **קודי קופון**: נוצרים באתר הניהול: קוד, כמות שימושים (1 / N / ללא הגבלה), תוקף, מה נותן (X חודשים חינם / הנחה %), למי (כללי / רשימת טלפונים). המשתמש מזין בהרשמה או במסך המנוי. מעקב מימושים.
- ניסיון חינם N ימים למי שנרשם בלי קופון (פרמטר באתר הניהול).

### 5.3 אתר ניהול (admin)
- משתמשים: חיפוש, סטטוס מנוי, הארכה ידנית, חסימה.
- מנויים והכנסות: MRR, churn, מימוש קופונים.
- קופונים ותקופות חינם (5.2).
- בריאות המערכת: צינור הנתונים לפי רשת (1.3), בריאות adapters (ריצה יומית מול האתרים), שיעור הצלחת העברות לפי רשת (מה-handoff results).
- קטלוג: תור העשרה (מוצרים חדשים בלי קטגוריה/מושג), אישור מושגים ותחליפים, תיקון סניפים בלי מיקום.
- תוכן: התראות מערכת ללקוחות, טקסטים.
- הרשאות: admin / support / data.

## 7. מה עוד צריך (שלא עלה בשיחה)
- **חוקי ותקינה**: מדיניות פרטיות, תנאי שימוש, נגישות (חובה), חוק הגנת הצרכן לעסקאות מתמשכות (ביטול מנוי קל, הודעה לפני חיוב), שמירת נתוני תשלום אצל הסולק בלבד. שימוש בנתוני שקיפות המחירים מותר, אבל לציין מקור ותאריך עדכון ליד כל מחיר.
- **מובייל**: השירות בסניף כ-PWA מיד (בלי חנויות); העברה לאונליין דרך אפליקציה בהמשך (LAUNCH.md).
- **חיפוש בעברית**: סבלנות לשגיאות כתיב, ניקוד, כתיב מלא/חסר, מילים נרדפות (קוטג'/גבינה לבנה). אינדקס טקסט (pg_trgm) + מושגים.
- **התראות**: מייל (Resend), וואטסאפ (Meta Cloud API, יקר יותר אבל ישראלי), Push ב-PWA.
- **מדידה**: אירועי משפך, A/B על הדיאלוג, שיעור השלמת סל ברשת (המדד הראשי), NPS קצר אחרי הזמנה.
- **תמיכה**: דיווח "המחיר לא נכון" מכל מוצר עם צילום; צ'אט/וואטסאפ תמיכה.
- **ביצועים**: `mapping/stats` איטי (TODO); תמחור 50 פריטים × 40 סניפים חייב להיות < 300ms → DB + אינדקס, לא קבצים.
- **אבטחה**: חתימת ה-payload בסימנייה (TODO), rate limit, OTP anti-abuse, סודות ב-env.
- **גיבויים**: DB יומי, קבצי מקור בארכיון.
