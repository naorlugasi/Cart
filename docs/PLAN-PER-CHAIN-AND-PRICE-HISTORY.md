# תוכנית: רשת-רשת בנפרד, והיסטוריית מחירים כשירות ללקוח

> החלטות נאור 22.9.2026: (1) כל רשת מטופלת בנפרד; רשת שנפלה מוצגת עם כוכבית "אין לנו מחירים עדכניים בגלל תקלה", בלי גבול ימים ובלי להוריד אותה. (2) גרף מחירים לאורך זמן לכל מוצר, כדף נפרד באתר, עם הערכת עלות. מסמך זה הוא התכנון; מה בונים ומתי מוכרע אחריו.

## חלק א: כל רשת בנפרד

### מה יש היום

- הריצה היומית (`scripts/daily-refresh.sh`) היא כל-או-כלום: רשת שנכשלה אחרי כל הניסיונות מפילה את הריצה, ואף רשת לא מתפרסמת.
- הורדה שנכשלה **לא מוחקת** את `data/prices/<chain>/catalog.full.json` של הריצה הקודמת. הקובץ הישן נשאר על הדיסק במרלוג.
- הבנייה (`scripts/build-products.mjs`) מוחקת את `data/catalogs/<chain>.json` של רשת שאין לה `catalog.full.json` בכלל, וההשוואה מציגה "אין מחירון לרשת זו".
- `sourceDate` (מ-22.9) אומר מאיזה רגע הקובץ של כל רשת.

### מה משתנה

**1. סטטוס לכל רשת, מפורסם.** קובץ חדש `data/pipeline-status.json` (חוזה, תוספת בלבד):

```json
{ "runAt": "2026-09-23T05:58:12+03:00",
  "chains": {
    "shufersal": { "status": "ok",     "sourceDate": "2026-09-23T03:40:00+03:00", "fetchedAt": "2026-09-23T05:56:10+03:00" },
    "victory":   { "status": "failed", "sourceDate": "2026-09-21T05:18:49+03:00", "fetchedAt": "2026-09-21T05:57:02+03:00",
                   "failedSince": "2026-09-22T05:55:00+03:00", "attempts": 4, "error": "laib: list returned 0 files" } } }
```

`status`: `ok` | `failed` (הורדה נכשלה, מוצג הקובץ האחרון) | `missing` (אין שום קובץ, הרשת לא בהשוואה). אותם שדות מועתקים גם לתוך `data/catalogs/<chain>.json` (`fetchStatus`, `failedSince`) כדי שצרכן שקורא רק קטלוג יראה אותם.

**2. הריצה לא נופלת על רשת אחת.** ב-`daily-refresh.sh`: רשת שנכשלה אחרי הניסיונות נרשמת ב-status ובלוג כאזהרה, והריצה ממשיכה לבנייה. הריצה נכשלת רק אם **כל** הרשתות נכשלו (תקלה אצלנו או ברשת הביתית) או אם הבדיקות אדומות.

**3. הבנייה מקבלת קובץ ישן.** רשת עם `status: failed` נבנית מה-`catalog.full.json` הקיים, בלי גבול ימים. `sourceDate` נשאר הישן. רק רשת בלי קובץ בכלל מוסרת, וגם אז בקול: שורה בלוג ו-`status: missing`.

**4. ניסיון חוזר לרשת בודדת במהלך היום.** job שני, קל, ב-launchd כל שעתיים בין 08:00 ל-20:00: קורא את status, ולכל רשת `failed` מנסה להוריד שוב. אם הצליח: בונה ומפרסם. הבנייה תמיד על כל 14 (היא לוקחת שניות), אבל רק הרשת שהתאוששה משתנה בפועל. כך פורטל של Laib שמפרסם ב-09:00 לא מחכה למחר.

**5. באתר.** הבקאנד מעביר `priceStatus` לכל רשת (`ok`/`failed`/`missing` + `sourceDate` + `failedSince`). הפרונט: **כוכבית אדומה** ליד שם הרשת, אותו רכיב של דמי המשלוח הלא ידועים, עם הטקסט: "אין לנו מחירים עדכניים לרשת זו בגלל תקלה. המחירים שמוצגים הם מ-<תאריך>". הרשת נשארת בדירוג.

**6. לדעת לטפל בכל רשת.** ל-`docs/RUNNER-MAC.md` נוסף "ספר רשתות": לכל פורטל, איך בודקים ידנית שהוא חי (`node scripts/fetch-prices.mjs <chain>`), מה השגיאות הידועות שלו (שופרסל איטית; Laib מפרסם מאוחר; קרפור בלי קובץ לסניף 471 בלילה), ומה עושים. healthchecks: check אחד לריצה כמו היום, ובנוסף שורה בלוג ובמייל היומי (אם נוסיף) עם רשימת הרשתות ב-`failed` ומאז מתי.

### מה לא משתנה

- אין שום פנייה לאתרי הרשתות. הניסיון החוזר הוא לפורטל שקיפות המחירים בלבד.
- רק מרלוג מגישה נתונים.
- בדיקות אדומות עדיין עוצרות פרסום.

### חלוקת עבודה (סאב-אייג'נטים)

| חבילה | קבצים | תלות |

| A1 סטטוס לכל רשת + הריצה ממשיכה | `scripts/daily-refresh.sh`, `scripts/fetch-prices.mjs` (כותב status), `docs/RUNNER-MAC.md` | אין |
| A2 הבנייה מקבלת קובץ ישן ומעתיקה סטטוס לקטלוג | `scripts/build-products.mjs`, `test/buildProducts.test.js`, `docs/PIPELINE-CONTRACT.md` | A1 (פורמט הקובץ) |

## חלק ב: היסטוריית מחירים כשירות ללקוח

### מה יש היום (וזה הרבה)

- מ-18.9 מרלוג טוענת **כל יום את כל הסניפים** של 11 רשתות (~990 סניפים) ל-DuckDB במק: `prices_current` (המחיר של היום בכל סניף) ו-**`prices_history`** (רק שינויים: מחיר, מאיזה תאריך, עד איזה תאריך). כלומר ההיסטוריה כבר נאספת, ברזולוציה של סניף, מאז 18.9.
- הקובץ: 942MB אחרי הריצה הראשונה, יגדל לאט (רק שינויים נשמרים). לא מגובה לשום מקום.
- האתר לא רואה אותו. הוא יושב במק.

### מה בונים

**1. גיבוי יומי של DuckDB ל-R2 (Cloudflare).** בסוף כל ריצה `prices.duckdb` נדחס ומועלה. זה גם הביטוח לכל ההיסטוריה: אם המק מת, לא איבדנו שנה. גודל: 1–3GB, גרסה אחת אחרונה + שבועית.

**2. ייצוא היסטוריה לקובץ לכל מוצר.** אחרי הטעינה, שאילתה אחת מפיקה לכל ברקוד ב-`products.json` (כ-7,200, גדל) קובץ `history/<gtin>.json`:

```json
{ "gtin": "7290000066318", "name": "במבה 80 גרם", "unit": "יח'",
  "series": { "shufersal": [["2026-09-18", 4.9], ["2026-10-02", 5.2]],
              "ramilevy":  [["2026-09-18", 3.9]] },
  "stores": { "shufersal": 380, "ramilevy": 62 },
  "updatedAt": "2026-09-23" }
```

הסדרה היא מחיר **חנות האונליין** של כל רשת (אותו מחיר שהאתר משווה), ורק נקודות שינוי, ולכן קובץ שנתי הוא כמה KB. בנוסף שדה "טווח בסניפים" (מינימום/מקסימום היום) שנותן ללקוח את "כמה זה עולה בסניפים" בלי לחשוף כל סניף. הקבצים מועלים ל-R2 עם CDN ציבורי; רק קבצים שהשתנו מועלים (השוואת hash).

**3. דף באתר: "מחיר לאורך זמן".** דף נפרד לכל מוצר (`/product/<gtin>/history`), קישור מכל שורה בהשוואה. גרף קווים, קו לכל רשת, טווח: 30 יום / 90 / שנה / הכל. מתחת: "הזול ביותר היום", "הכי נמוך שראינו ומתי", "עלה/ירד ב-X% בחודש". הדף קורא קובץ אחד מה-CDN, אין API ואין מסד נתונים בענן. הפרונט יכול לצייר עם ספרייה קלה (uPlot, 40KB) או SVG ידני.

**4. אחרי שנה.** אותם קבצים, אותו דף. שאלות כמו "מה עלה הכי הרבה השנה" הן שאילתה אחת ב-DuckDB במק שמפיקה קובץ סיכום `history/summary.json` (עשרת המוצרים שעלו, שירדו, מדד סל ממוצע לפי רשת). זה יכול להיות דף "מגמות" נפרד, בלי תשתית נוספת.

### עלויות

| רכיב | כמות | עלות לחודש |

| R2 אחסון: היסטוריה לכל מוצר | ~7,200 קבצים × ~5–30KB אחרי שנה ≈ 0.2GB | ~$0.01 |
| R2 אחסון: גיבוי DuckDB | 3GB אחרונה + 4 שבועיות ≈ 15GB | ~$0.25 |

| R2 יציאה (egress) | חינם ב-Cloudflare | $0 |

| מרלוג: דיסק | DuckDB גדל ~50–150MB לחודש (רק שינויים) | $0 (36GB פנויים) |

| **סה"כ** | | **~$0.5–2 לחודש** |

ההנחה המרכזית: לא שומרים כל יום את כל המחירים אלא רק שינויים, וזה מה ש-`prices_history` כבר עושה. הסיכון היחיד לעלות: אם נרצה בעתיד גרף **לכל סניף** ולא רק לאונליין, מספר הקבצים גדל פי 100 ואז זה עדיין R2, אבל ~$5–10 לחודש.

מה שלא צריך ואין סיבה להוסיף: Postgres בענן, שרת API להיסטוריה, שירות גרפים בתשלום.

### סיכונים

- **חור בהיסטוריה** כשמרלוג לא רצה (כמו 19.9 ו-21.9). זה לא ניתן להשלמה אחורה: הפורטלים מחליפים קבצים כל יום. ההגנה היא חלק א' + ההתחברות האוטומטית שנדחתה. הגרף פשוט לא יראה נקודה באותם ימים, וזה נכון.
- **שינוי ברקוד/שם** של מוצר: ההיסטוריה לפי gtin, ומוצר שמחליף ברקוד מתחיל סדרה חדשה. מקובל.
- **מבצעים**: ההיסטוריה היא מחיר מדף. מבצע "3 ב-10" לא בגרף. אפשר להוסיף שכבה "היה במבצע" מ-PromoFull בשלב שני.
- **R2 עוד לא הוקם** (הוחלט 16.9, לא בוצע). זו הפעולה הראשונה, וצריך חשבון Cloudflare ומפתח API ב-`pipeline.env` במרלוג.

## סדר מוצע

1. **A1–A3** (רשת-רשת בנפרד) ו-**B0** (R2) במקביל: A משפר את הטריות מחר בבוקר, B0 הוא תנאי לכל השאר.
2. **A4–A5** (הכוכבית באתר) ו-**B1–B2** (גיבוי וייצוא).
3. **B3** (הדף ללקוח). מרגע זה יש היסטוריה חיה מ-18.9 והלאה.
4. **B4** כשיש חודש של נתונים.

מה שדורש החלטה לפני שמתחילים: חשבון Cloudflare (מי פותח, איזה כרטיס), ושם הדומיין לקבצים הציבוריים (`data.salhacham.co.il` או דומיין של Cloudflare).
