# אינדקס קטלוג מקומי (DuckDB)

**כלי מקומי בלבד.** לא חלק מהצינור היומי (pipeline/*), לא נטען על ידי מריץ המחירים, ולא נכנס ל-git -
`data/local/` ב-`.gitignore`. כל סשן בונה אותו אצלו, שואל אותו, וזורק. למה בכלל: כל סשן שעבד על הנתונים
האלה כתב סקריפט חד-פעמי משלו לכל שאלה, בהגדרות לא עקביות (סשן אחד מדד 19% מוצרים בלי מחיר, אחר - 23%).
האינדקס הזה נותן הגדרה אחת, מוסכמת, לכל שאלה חוזרת - ה-SQL של כל view למטה *הוא* ההגדרה.

## בנייה

```
node scripts/index-build.mjs
```

קורא את `data/products.json` ואת `data/prices/<chain>/catalog.full.json` של 14 הרשתות מ-`DATA_ROOT`
(משתנה סביבה; ברירת מחדל `/Users/naorlugassi/Projects/Cart/data` - המחשב האמיתי, כי ה-worktree של
הסשן לא נושא את `data/prices/` המתעלם-מ-git). קונספטים/קטגוריות/רשומות מאומתות נטענים מה-checkout הזה
עצמו (`config/concepts`, `config/categories`, `config/products`), כמו כל סקריפט אחר תחת `src/catalog`.
הפלט: `data/local/catalog.duckdb`. החלק היקר - פענוח ~130 אלף שמות גולמיים מול 1000 הקונספטים - לא
נשמר בין בניות; כל בנייה מחשבת מחדש ומדפיסה כמה זמן זה לקח.

## שאילתות מוכנות

```
node scripts/index-query.mjs why <gtin>          # כל שם שרשת נתנה לברקוד, למה הוא מתפרש, גודל, מחלקה, תווית, אימות
node scripts/index-query.mjs coverage            # כיסוי מחיר - סה"כ, לפי רשת, לפי מחלקה
node scripts/index-query.mjs no-concept [--dept <מחלקה>]   # מוצרים בלי קונספט, עם הפירוט למה (תיקו / אין התאמה)
node scripts/index-query.mjs unsized [--concept <id>]      # מוצרים בקונספט עם יחידת מידה שלא קיבלו גודל
node scripts/index-query.mjs sellers <gtin>      # אילו רשתות מוכרות ברקוד - מוגשות / לא מוגשות בנפרד
node scripts/index-query.mjs concept <id>        # כל המוצרים של קונספט + הסיכום שלו
node scripts/index-query.mjs sql "<query>"       # כל שאילתה חופשית נגד הטבלאות/ה-views
```

הפלט הוא טבלת טקסט מיושרת לטרמינל, לא JSON - זה כלי לקרוא בו, לא לפרסר.

## טבלאות

- `products` - קטלוג מאוחד, שורה לכל `id` (gtin רגיל או `c-<concept>` לכרטיס קונספט שקול).
- `chain_items` - כל שורה גולמית של כל רשת (gtin, שם, מחיר, האם שקיל, מתי עודכן, כמה מבצעים).
- `name_concepts` - מה כל שם גולמי, בפני עצמו, פותר אליו: קונספט שהוקצה (רק כשההתאמה חד-משמעית),
  רשימת הקונספטים שהתאימו (תיקו אם 2+), וגודל שפוענח מהשם. זה החלק היקר של הבנייה.
- `concepts`, `chains` (`served` = ברשימת 7 הרשתות שהאתר באמת מציע: שופרסל, רמי לוי, קרפור, יוחננוף,
  חצי חינם, ויקטורי, אושר עד), `labels` (תוויות מחלקה שנסקרו ידנית), `verified` (רשומות שאומתו).

## ה-views וההגדרה המוסכמת שלהם

כל הגדרה חיה כהערה ב-SQL עצמו (`scripts/index-build.mjs`, קבוע `VIEWS`) - כאן רק התמצית:

- **`v_coverage`** - "יש מחיר" = הברקוד מופיע בשורה כלשהי ב-`chain_items` של אותה רשת. שלושה חלקים
  (עמודת `scope`): `overall` (שורה אחת - סה"כ מוצרים עם gtin מול כמה יש להם מחיר ברשת מוגשת/בכל רשת),
  `chain` (שורה לרשת - כמה gtin-ים ייחודיים היא מתמחרת), `department` (שורה למחלקה - כמה מהמוצרים שלה
  בלי מחיר ברשת מוגשת / בכל רשת). **זה המספר לצטט על "כיסוי" - לא יחס הקונספטים הבר-השוואה בכל הקטלוג
  (27%), שהוא מספר אחר לגמרי ונמוך בהרבה** (docs/PLAN-PRODUCT-TRUTH.md, "קונספט בר-השוואה ← סל אמיתי").
- **`v_no_concept`** - שורה לכל (מוצר בלי `concept_id`) × (אחד השמות הגולמיים שלו), עם `reason`: `tie`
  (השם התאים ל-2+ קונספטים), `no-match` (לא התאים לאף אחד), או `resolved-no-consensus` (השם הזה לבדו
  כן פתר לקונספט יחיד, אבל ההצבעה בין כל השמות של הברקוד - docs/CONCEPTS.md §3 - לא הגיעה לקונצנזוס).
- **`v_unsized_in_sized_concept`** - הקונספט של המוצר מצהיר `size_unit`, אבל למוצר עצמו אין גודל.
  מחולק שקיל/לא-שקיל (`is_weighted`) - אצל שקיל זה צפוי (אין אריזה קבועה), אצל לא-שקיל זה פער אמיתי.
- **`v_concept_sizes`** - לכל קונספט: כמה מוצרים, כמה מהם עם גודל, מחיר-בסיס חציוני, וכמה רשתות שונות
  מוכרות מוצר כלשהו של הקונספט (נספר דרך `chain_items`, לא עמודת `products.chains` שסופרת רשתות
  למוצר בודד אחד בלבד).
- **`v_barcode_sellers`** - לכל gtin שמופיע אצל רשת כלשהי: רשימת הרשתות שמוכרות אותו, בנפרד מוגשות
  ולא-מוגשות.
